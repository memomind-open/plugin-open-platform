# Source Review Packages and External Headers

GlassSDK generates a `.gmp`, a `.review.json`, and a `.review-source.enc` during
compilation. When you select the GMP and generate a sharing QR code in Studio,
Studio combines these artifacts into a review ZIP. It does not rebuild the plugin
or collect the current working tree. Rebuild after changing source or dependencies
before sharing the package again.

## One ZIP for distribution and review

Studio exports one ZIP containing the unencrypted GMP, `review.json`, and
`source.enc`. Source files and complete headers are compressed together with
TAR+XZ, then encrypted using the public key in
`build-host/tools/review_public_key.json`. Install `PyNaCl` once:

```sh
python3 -m pip install PyNaCl
```

The public SDK never includes the private key. Studio executables and phone apps
need no key: they retain the complete ZIP and extract only runtime components.
Phone resharing preserves the original ZIP bytes, including encrypted source.
Source-only updates are transferred as complete ZIPs as well.

Internal reviewer scripts automatically use their private key. An external audit
machine must supply an authorized key with `--private-key /secure/review-key.json`
or `GM_REVIEW_PRIVATE_KEY`. Decryption restores the original source/header bytes;
GMP encryption and Bluetooth protocol changes are not required. Encryption protects
source confidentiality, not reviewer approval or source-to-binary authenticity.

## Including external headers

All files in the GCC/Ninja dependency list are captured verbatim, including direct,
transitive, and system headers. Header contents are not pruned, and dependencies
are not removed based on whether their functions or types are referenced.
Project sources, resources, and SDK headers are also retained. For shared directories
outside the project, only dependencies read by GCC are collected; the entire
shared directory is not copied.

External dependencies must be inside the SDK, the selected toolchain, or the
explicit `--source-root`. The source root defaults to the directory selected by
`--project`. For shared headers outside that directory, set it to a common ancestor
of the project and its dependencies.

For example:

```text
/work/
├── apps/my_plugin/
│   ├── manifest.json
│   └── main.c
└── shared/include/
    ├── shared.h            Included by main.c
    ├── detail/config.h     Included transitively by shared.h
    └── unused.h            Not read by GCC; not collected
```

Run from the GlassSDK directory:

```sh
python3 build.py build \
  --project /work/apps/my_plugin \
  --source-root /work \
  --include-dir /work/shared/include
```

- `--source-root` defines the boundary for dependency collection and relative path
  restoration. It does not add compiler include search paths.
- `--include-dir` adds a GCC include search directory and can be repeated. Each
  directory must be inside `--source-root`.
- If a relative `#include` already resolves correctly, its corresponding
  `--include-dir` can be omitted. The source root must still cover the dependency.
- Relative argument paths are resolved from the current working directory. Quote
  paths containing spaces.
- `--source-root` and `--include-dir` require `--project`. For a project under
  `examples` that needs these options, pass its directory through `--project`.

By default, the command writes the three matching artifacts to
`/work/apps/my_plugin/.build/my_plugin/`. A dependency outside the SDK, toolchain,
and declared source root causes the build driver to report
`Dependency outside SDK/toolchain/source root` and exit with an error. It is not
silently omitted. A GMP may already have been generated by that point; wait for
the entire build command to succeed before sharing a review package.

## Extracting and rebuilding

Run from the plugin_studio repository:

```sh
python3 scripts/extract_review.py /path/to/review.zip --output /tmp/plugin-audit
```

New packages contain complete system header files, so extraction does not need
locally installed toolchain headers. Project and shared dependency paths are
restored under `source/workspace/`, preserving their relative layout. SDK build
tools are restored under `source/SDK/`.

Inspect the `rebuild` argument list in `source/build.json`, then run it from the
extracted `source` directory. For the example above:

```sh
python3 SDK/build.py build \
  --project workspace/apps/my_plugin \
  --source-root workspace \
  --include-dir workspace/shared/include
```

Rebuilding still requires a matching GCC compiler and linker, Python, CMake, and
Ninja. The build driver validates bundled system dependencies and uses `-nostdinc`
with the recorded package-local system include directories. Use the extraction
script's `--compare-gmp` option to compare the rebuilt GMP with the packaged GMP.
Older packages containing only system header hashes still require
`--toolchain-bin` for extraction.

## Runtime behavior

Source attachments and review metadata are used only for source review, integrity
checks, and restoration. Studio's simulator loads the compiled GMP. After
validating the review ZIP, the phone places only the GMP in its device runtime slot
and transfers it using the existing Bluetooth protocol. Source files, headers,
and review metadata are not included in the glasses' runtime payload.
